# 実績リードタイム集計 と Hs 取込（提案版・実装済）

「1 SHOP あたり 4日」という前提が妥当かをデータで確認し、SHOP ごとに実測値へ
置き換えられるようにする機能。ブランチ `develop`。

全体の位置づけは [フェーズ2_提案まとめ.md](フェーズ2_提案まとめ.md) §2 を参照。

---

## 1. 何を作ったか

| # | 内容 |
|---|---|
| 1 | FLEXSCHE の `Hs` 列（標準時間）を `t_routing.hs` に取込 |
| 2 | JND(実績) から SHOP 別の実績リードタイムを集計し `t_shop_lt_stat` に保存 |
| 3 | 実績値を「推奨値」として画面に出し、納得したものだけ `m_shop_lt` に採用できる |
| 4 | `LT_MODE` で「マスタ固定」「実績集計」を切り替えられる |

**実績値を自動で本番計算に流し込むことはしない。** 理由は §5 の実測結果のとおりで、
そのまま切り替えると赤が倍増する。まず「見る」ところから始める設計にした。

## 2. Hs について

`Hs = Standard Hours`（標準時間）。その工程を標準的な条件でこなすのに必要な作業時間。

FLEXSCHE 結果出力 CSV の 32 列目に元から存在し、これまで読み飛ばしていた。
今回の取込で実データを確認した結果は次のとおり。

| 項目 | 値 |
|---|---|
| 行数 | 321,980 |
| 欠損 | **0 件** |
| 平均 | 3.67 h |
| 最大 | 1,340 h |

**Hs はリードタイムではない。** 正味の作業時間であって、順番待ち・段取り・運搬・
検査待ちを含まない。実測でも Hs 中央値は SHOP によって 0.5〜8h 程度で、8h/日 換算では
1日にも満たない。これを日数に換算して LT に使うと、リードタイムを一桁小さく
見積もることになる。

一方で Hs 1,340h（約167人日）のような工程は、待ちがゼロでも数ヶ月かかる。
Hs の使いどころは全体の精度向上ではなく、**この手の「絶対に4日では終わらない工程」を
確実に検出すること**にある。今回は取込と参考表示までを実装し、
LT 算出式への組み込みは客先確認（§7）の後に判断する。

## 3. 実績リードタイムの求め方

### 3.1 どの区間を測るか

`工程着手日付 → 工程完了日付` の差は中央値 0 日で、これは「作業を実施した日」の記録。
待ち時間を含まないためリードタイムにならない。

そこで **前工程の完了実績 → 当工程の完了実績のインターバル**を採る。

```
… ─┬─ SHOP A 完了(実績) ────────────── SHOP B 完了(実績) ─┬─ …
    └──────────  B のリードタイム  ──────────┘
```

### 3.2 バッファ計算と単位を揃える

バッファ計算（`calc.ts`）は次の2つの前提で動いている。集計側もこれに合わせないと、
採用した値がそのままズレる。

1. **連続する同一 SHOP は1コマに圧縮**して LT を積む
   → 集計側も同じ圧縮をしてからインターバルを取る
2. **残日数は稼働日ベース**（`m_calendar` の休日を除く）
   → 集計側も稼働日で数える

### 3.3 除外するもの

| 条件 | 理由 |
|---|---|
| 先頭コマ | 前工程が無いのでインターバルが定義できない |
| コマ内に実績が欠けている行がある | そのコマはまだ完了していない |
| 前後どちらかの実績が無い | 区間が飛んでいるので前後をつなげない |
| 負のインターバル | 実績日付の逆行。データ不整合 |
| `LT_ACTUAL_MAX_DAYS`（既定365日）超 | 長期停止・データ不整合 |

同日完了（0日）は正常値として数える。

### 3.4 出力

SHOP ごとに `n / p50 / p75 / p90 / 平均`、参考として Hs 中央値を出す。
分位点は線形補間。

## 4. 採用の流れ

```
t_routing(JND実績) ──集計──> t_shop_lt_stat ──推奨値──> 画面 ──人が判断──> m_shop_lt
```

`m_shop_lt` は手入力の標準LTマスタで、**集計値で黙って上書きしない。**
現場が意図して入れた値を機械が消してしまうのを防ぐため、実績より手入力を常に優先する。

有効なLTの決まり方：

| 優先 | 出どころ | 条件 |
|---|---|---|
| 1 | `m_shop_lt`（手入力） | 登録があれば常にこれ |
| 2 | 実績の分位点 | `LT_MODE=actual` かつサンプル数が `LT_MIN_SAMPLES` 以上 |
| 3 | `m_param.SHOP_LT_DAYS` | 上記に当たらない SHOP |

推奨値は 0 日にはせず下限 1 日に丸める。

## 5. 実データでの検証結果

部品 24,163 件・工程 321,980 行（うち JND実績あり 93,937 行）。

### 5.1 集計結果

| 項目 | 値 |
|---|---|
| 集計できた SHOP | 153 |
| サンプル数 | 35,648 |
| 集計時間 | 約5秒 |
| **実績中央値が既定LT(5日)を超える SHOP** | **133 / 153** |
| それらの SHOP が占めるサンプル | **72.6%** |

SHOP 別の実測（サンプル数上位）:

| SHOP | 名称 | n | p50 | p75 | p90 | Hs中央値 |
|---|---|---|---|---|---|---|
| 7P21 | 検査（素材確認） | 7,226 | 7 | 14 | 27 | 0.7h |
| 7P32 | 検査（処理） | 4,715 | 5 | 9 | 15 | 0.5h |
| 7P31 | 検査（浸透探傷） | 3,137 | 3 | 7 | 16 | 0.8h |
| 8A56 | 組立作業 | 2,403 | 9 | 22 | 49 | 1.2h |
| 8A25 | 自主検査 | 1,662 | 12 | 28 | 49 | 3.5h |
| 8A21 | 自主検査 | 1,294 | 24 | 68 | 127 | 5.0h |
| 8633 | — | 610 | 0 | 0 | 0 | 0h |

**中央値が 0 日の SHOP から 200 日超の SHOP まで開いている。**
一律の日数でカバーできる分布ではない、というのが今回のいちばんの結論。

### 5.2 全部を実績に切り替えるとどうなるか

`LT_MODE=actual` にして全部品を再計算した結果。

| | 緑 | 黄 | 赤 |
|---|---|---|---|
| 固定（現行・5日） | 15,754 | 423 | 7,986 |
| **実績（p50）** | 8,616 | 215 | **15,332** |

**赤が 7,986 → 15,332 件（全体の63%）に倍増する。** バッファの最小値は −4,915 日。

これは実績集計の不具合ではなく、次の性質が重なった結果と考えている。

- 実績インターバルには **外注に出ている期間・材料待ち・部署間の停滞がすべて入る**。
  長い SHOP は `820L M/C加工` 219日、`82P0 自主確認` 255日、`8244 マシニングセンター加工`
  143日といった値になる（いずれも外注系と思われる）
- 残工程が10コマある部品だと、これらの p50 を単純に足し上げて 1,000 日超になる
- 全 SHOP が同時に中央値を引くわけではないので、**分位点の単純合計は悲観側に偏る**

つまり「実績LTをそのまま全体に適用する」のは正しくない。
今回の実装で `LT_MODE` の既定を `fixed` にし、SHOP 単位の採用を人の判断に残したのは
この結果を見越してのこと。**この数字自体が『4日（現状5日）は妥当か』への回答**になる。

## 6. 実装

### 6.1 スキーマ

マイグレーション `20260814100000_lt_actual_and_hs`。

```prisma
model Routing {
  hs Decimal? @db.Decimal   // FLEXSCHE Hs列（時間）
}

model ShopLtStat {          // t_shop_lt_stat（バッチ再生成）
  shop       String   @id
  n          Int
  p50 p75 p90 mean    Decimal
  hsMedian   Decimal?
  computedAt DateTime
}
```

### 6.2 パラメータ（`m_param`）

| キー | 既定 | 意味 |
|---|---|---|
| `LT_MODE` | `fixed` | `fixed`＝マスタ固定 / `actual`＝実績集計を併用 |
| `LT_ACTUAL_PERCENTILE` | `p50` | 採用する分位点（`p50` / `p75` / `p90`） |
| `LT_MIN_SAMPLES` | `10` | これ未満のサンプルしかない SHOP は推奨しない |
| `LT_ACTUAL_MAX_DAYS` | `365` | これを超えるインターバルは異常値として除外 |

`npm run seed` は不足キーだけを足す（既存値は上書きしない）。

### 6.3 ファイル

| ファイル | 役割 |
|---|---|
| `backend/src/lt/lt.logic.ts` | 集計の純ロジック（分位点・インターバル抽出・LTマップ組立） |
| `backend/src/lt/lt.logic.test.ts` | 上記のユニットテスト 24件 |
| `backend/src/lt/lt.service.ts` | Prisma 読み書き、推奨値の算出、採用処理 |
| `backend/src/lt/lt.controller.ts` | `/api/lt/*` |
| `backend/src/masters/masters.util.ts` | `LT_MODE` に応じた SHOP別LTマップの組立 |
| `backend/src/etl/etl.service.ts` | Hs 取込 |
| `frontend/src/components/LtStats.tsx` | 実績LT画面 |
| `frontend/src/lib/lt.view.ts` | 表示ロジック（乖離判定・絞り込み・並べ替え） |

### 6.4 API

| メソッド | パス | 権限 | 内容 |
|---|---|---|---|
| GET | `/api/lt/stats` | 認証 | SHOP別の実績・現在値・推奨値・乖離 |
| POST | `/api/lt/recompute` | 管理者 | 実績LTを集計し直す |
| POST | `/api/lt/adopt` | 管理者 | 推奨値を `m_shop_lt` に反映（`shops` 未指定なら全件） |

採用は1件ずつ監査ログ（`lt.adopt`）に残る。いつ誰がどの分位点を何件のサンプルに基づいて
採用したかが後から追える。

### 6.5 バッチ

```bash
npm run etl    # CSV取込＋算出＋実績LT集計（実績が変わるのは取込時だけなので同時に回す）
npm run lt     # 実績LT集計のみ
```

## 7. 画面

サイドバー「実績LT」（管理者のみ）。`/lt`。

- 上部に要約：集計SHOP数 / サンプル数 / **既定LTで足りないSHOP数** / 現在の方式
- 表は SHOP 別に `件数 / 中央値 / p75 / p90 / 平均 / Hs中央値 / 現在値 / 実績−現在 / 推奨`
- 「実績−現在」がプラス＝実績のほうが長い＝**バッファを多めに見積もっている（緑に見えて危ない）**。
  赤字で表示する
- 行ごとの「採用」と、上部の「推奨値をまとめて採用」
- 既定の並びは乖離の大きい順。「実績のほうが長いSHOPだけ」で絞れる

## 9. 未確定・次にやること

### 9.1 客先に確認したいこと

- Hs の単位は人時か時間か（複数人作業をどう数えているか）
- Hs は正味作業のみか、段取りを含むか
- 実績工数（Hs の消化率）が別途取得できるか
- SHOP ごとの要員数・稼働時間が取得できるか（Hs を日数に換算するのに要る）

### 9.2 実装として詰めたいこと

| 項目 | 内容 |
|---|---|
| **外注工程の切り分け** | 実績インターバルに外注滞留が丸ごと入っている。`out_date`→`in_date` と `m_vendor.return_lt` で別建てにすれば、内製工程の実力値が見えるはず。§5.2 の赤倍増はここが主因と考えている |
| **合計の悲観バイアス** | 分位点を残工程分そのまま足すと悲観に寄る。部品単位の実績総LT（最初→最後）と突き合わせて補正係数を出したい |
| 集計期間 | 現在は全期間。直近1〜2年に限る指定があると、体制変更後の実力を見られる |
| SHOP×JOB 粒度 | 現在は SHOP 単位（`m_shop_lt` が SHOP キーのため）。JOB まで分けるならマスタ側も要拡張 |
| Hs の算入 | `待ち日数 + Hs ÷ 有効稼働時間` の C・D 方式。§7.1 の確認結果とキャパマスタが前提 |
| 部品詳細での方式比較 | 「固定なら +3日（緑）だが実績なら −6日（赤）」の併記。切り替えの説得力はここから出る |

### 9.3 ついでに直したもの

`PartDetail.tsx` の「残Shop数 × 4日/Shop」は 4 がハードコードされており、
`SHOP_LT_DAYS` や `m_shop_lt` を変えても表示に反映されていなかった。
算出済みの残日数とバッファから所要日数を逆算し、SHOP 別LT の合計を正しく出すよう修正した
（平均 n 日/Shop を併記）。
