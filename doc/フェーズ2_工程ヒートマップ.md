# 工程ヒートマップ（フェーズ2・提案実装）

「このジョブ・このショップに今後部品が集中しそう」を一目で見るための画面。
`develop` ブランチに提案版として実装した。**仕様は未確定**で、閾値の考え方と
UI の粒度は客先レビューを経て調整する前提。

- 画面: `/heatmap`（サイドバー「**工程ヒートマップ**」）
- API: `GET /api/heatmap`, `GET /api/heatmap/cell`
- 既存の算出（`t_part_status` / `t_timeline`）は変更していない

---

## 1. 何を「詰まり」と定義したか

「詰まり」には性質の違う2つが混ざっているため、画面上で分けて並べている。

| | 定義 | データ源 | 画面上の位置 |
|---|---|---|---|
| **今すでに詰まっている** | その工程で仕掛中の部品数と平均滞留日数 | `t_routing.wip_flag` + `t_part_status.stagnant_days` | 左端の固定列「現在の滞留」 |
| **これから詰まりそう** | いつ何件その工程に入ってくる予定か | `t_routing.plan_start` / `plan_end` | 右側の週次ヒートマップ |

後者は生産管理でいう**山積み表**にあたる。

## 2. 集計仕様

### 2.1 対象データ

`t_routing` のうち **`actual_end IS NULL`（未完了）かつ `shop` が非 NULL** の行。
さらに、表示期間に掛かる行と、現在仕掛中（`wip_flag`）の行だけを SQL で絞り込む。

②算出結果テーブルの再生成は不要で、取込済みデータからオンデマンドに集計する。
つまり **`POST /api/recompute` を待たずに常に最新**になる。

### 2.2 数え方（mode）

| mode | 定義 | 用途 |
|---|---|---|
| `arrival`（流入・既定） | `plan_start`（無ければ `plan_end`）が属する期間に1件計上 | 「同じ時期に何件入ってくるか」 |
| `occupancy`（在席） | `[plan_start, plan_end]` と重なる全期間に計上 | 実際の混み具合 |

同じ部品が同一工程に複数行を持つことがあるため、**セル内は OS_ID でユニーク化**する
（＝件数は「部品数」であって「工程行数」ではない）。

### 2.3 軸

- 横軸: `unit=week`（月曜始まり）または `unit=day`。既定 12 週
- 縦軸（`groupBy`）:
  - `shop`（既定）— SHOP 単位
  - `job` — SHOP×JOB まで分割
  - `part` — **部品単位**（縦が部品、横が期間。その期間に滞在予定の SHOP コードを表示。色は部品自身の緊急度）

部品単位は行数が多くなるため、API は優先度順に **上位 200 行**だけ返す（`totalRows` で全体件数を通知）。

### 2.4 色の決め方（ここが設計の肝）

**工程単位（shop / job）** では、絶対件数ではなくその工程自身の平常時と比べる。

```
baseline = max( 件数が0でない期間の平均件数, 1 )     ← 平常時
ratio    = count / baseline
相対判定  = ratio >= crit → crit / >= alert → alert / >= warn → warn / else low
絶対判定  = count >= absCrit → crit / >= absAlert → alert / >= absWarn → warn / else low
           （閾値0は「使わない」。既定は全て0＝無効）
level    = count < minCount → none（判定なし・灰）
           それ以外は 相対判定と絶対判定の厳しい方
```

**部品単位（part）** では混雑度ではなく、部品自身の緊急度（赤/黄/緑）で塗る。

#### なぜ「件数が0でない期間の平均」なのか

当初は期間内の**中央値**を分母にしていたが、実データで検証したところ
**判定済みセルの33%が「過密」になり、画面がほぼ真っ赤で使い物にならなかった。**

原因は計画データの性質にある。FLEXSCHE の計画は数週間先までしか無く、
12週表示すると後半はほぼ全て0件になる。中央値も全期間平均も0に張り付き、
分母が1（0除算回避のクランプ値）に落ちて、あらゆるセルが「平常時の数十倍」に
なってしまう。

**「実際に部品が入る期間」だけを分母の母数にする**ことで解決した。

#### パラメータ（`m_param`／マスタ管理のパラメータ設定から変更可）

| キー | 既定 | 意味 |
|---|---|---|
| `HEAT_WEEKS` | `12` | 既定表示週数 |
| `HEAT_MIN_COUNT` | `3` | この件数未満は判定しない |
| `HEAT_LEVEL_WARN` | `1.2` | 平常時の何倍で黄 |
| `HEAT_LEVEL_ALERT` | `1.5` | 何倍で赤 |
| `HEAT_LEVEL_CRIT` | `2` | 何倍で濃赤 |
| `HEAT_ABS_WARN` | `0` | 件数そのものが何件で黄（0=使わない） |
| `HEAT_ABS_ALERT` | `0` | 件数そのものが何件で赤（0=使わない） |
| `HEAT_ABS_CRIT` | `0` | 件数そのものが何件で濃赤（0=使わない） |

### 2.5 セルの中身

- **工程単位**: 件数を大きく表示し、その下に赤／黄／緑の内訳を細い積み上げバーで出す
- **部品単位**: その期間に滞在予定の SHOP コード（複数あればカンマ区切り）

行のソートは ピーク水準 → ピーク倍率 → 現在の仕掛数 の順で、混んでいる工程が上に来る。

### 2.6 絞り込み

機種・分類・担当者・緊急度（赤/黄/緑）。工程員は自分の担当が初期選択される。
絞り込みはヒートマップとセル内訳の両方に効く。

## 3. UI（プロト版）

客先レビュー用に、以下を追加した。

| 項目 | 内容 |
|---|---|
| **マップ風レイアウト** | 左に工程（または部品）、右に日程。セルは件数0も含め**全面を色で塗る**（予定なしは薄灰） |
| **長い工程名** | SHOP_JOB マスタの制御文字・連続空白を除去し、行見出しは1行省略表示 |
| **工程クリック** | 行見出しクリックで `/parts?shop=xxxx` に遷移し、**その工程に現在滞在している部品**を一覧表示 |
| **セルクリック** | 工程単位では従来どおり右ドロワーで内訳。部品単位では部品詳細へ |
| **表示切替** | ツールバーで SHOP / SHOP×JOB / **部品** を切替 |

## 4. API

### `GET /api/heatmap`

| パラメータ | 値 | 既定 |
|---|---|---|
| `mode` | `arrival` \| `occupancy` | `arrival` |
| `unit` | `week` \| `day` | `week` |
| `groupBy` | `shop` \| `job` \| `part` | `shop` |
| `count` | 1〜26（週）/ 1〜60（日） | `HEAT_WEEKS` |
| `kishu` / `category` / `owner` | 文字列 | なし |
| `color` | `red` \| `yellow` \| `green` | なし |

レスポンスに `totalRows`（切り捨て前の行数）と、各行の `sub`（SHOP コード等の副見出し）を含む。

### `GET /api/heatmap/cell`

セルの内訳。`shop`・`from`・`to` が必須、`groupBy=job` のときは `job` も必須。
該当部品を**バッファ昇順**（次に残日数昇順）で最大 300 件返す。
