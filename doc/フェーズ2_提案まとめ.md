## 1. 工程の詰まりの可視化

「このジョブ・このショップに今後部品が集中しそう」を一目で見るための画面。
仕様と実装内容は [フェーズ2_工程ヒートマップ.md](フェーズ2_工程ヒートマップ.md) に分離した。

要点だけ再掲する。

- 縦軸 SHOP（または SHOP×JOB）、横軸 週（または日）で部品件数を積み上げる
- 「今すでに詰まっている量（仕掛数・平均滞留日数）」を左端の固定列に置き、
  「これから流れ込む量」を右に展開する
- 色は絶対件数ではなく、**その工程の平常時（部品が流れている週の平均件数）に対する倍率**で
  決める。SHOP ごとの規模差を吸収するため。「N件以上で赤」の絶対件数指定も
  パラメータで併用できる（既定は無効）
- セルをクリックすると、その工程・その週に来る部品がバッファ昇順で出る

## 2. リードタイム精度向上（実績LT / Hs）

### 2.1 現状

1 SHOP あたりの所要日数は既定 4 日（`m_param.SHOP_LT_DAYS`）、SHOP 別に
`m_shop_lt.lt_days` で上書きできる。バッファ＝残日数 − 残SHOP数×LT。

> `PartDetail.tsx` の「残Shop数 × 4日/Shop」表示は 4 がハードコードされており、
> `SHOP_LT_DAYS` や `m_shop_lt` を変更しても表示に反映されなかった。→ 修正済み。

### 2.2 Hs とは

**Hs = Standard Hours（標準時間・標準工数）**。その工程を標準的な条件でこなすのに
必要な作業時間。

**FLEXSCHE の CSV には既に `Hs` 列が存在する**（32列目、`JND` と `計上日` の間）。
取込を実装して全 321,980 行を確認した結果、**欠損は 0 件**、平均 3.67h、最大 1,340h。
同じ SHOP×JOB でも部品ごとに値が異なる。

### 2.3 「Hs にすればリードタイム精度が上がる」の落とし穴

Hs は**正味の作業時間**であって、リードタイムではない。

主要 SHOP の Hs 中央値は 0.5〜8h で、8h/日換算すると 1 日にも満たない。
現行想定 LT との差は作業ではなく、**順番待ち・段取り・運搬・検査待ち**である。
Hs をそのまま日数換算するとリードタイムを一桁小さく見積もることになり、危険な楽観を生む。

```
LT(日) = 待ち日数（工程の混雑で決まる） + Hs ÷ 1日あたり有効稼働時間
              ↑ 支配項                        ↑ Hs が効く項
```

Hs の価値は全部品の精度向上ではなく、**「4日では絶対に収まらない工程」を確実に検出する**
ことにある（Hs 1,340h ＝ 約167人日の工程は、待ちがゼロでも数ヶ月かかる）。

### 2.4 実績データによる「4日」の検証（実装して確認済み）

JND(実績) から前工程完了 → 当工程完了のインターバルを SHOP 別に集計した。
サンプル **35,648件 / 153 SHOP**。

| SHOP | 名称 | n | 中央値 | p75 | p90 | Hs中央値 |
|---|---|---|---|---|---|---|
| 7P21 | 検査（素材確認） | 7,226 | 7日 | 14 | 27 | 0.7h |
| 7P32 | 検査（処理） | 4,715 | 5日 | 9 | 15 | 0.5h |
| 7P31 | 検査（浸透探傷） | 3,137 | 3日 | 7 | 16 | 0.8h |
| 8A56 | 組立作業 | 2,403 | 9日 | 22 | 49 | 1.2h |
| 8A21 | 自主検査 | 1,294 | **24日** | 68 | 127 | 5.0h |
| 8633 | — | 610 | **0日** | 0 | 0 | 0h |
| 820L | M/C加工 | 214 | **219日** | — | 288 | — |

- SHOP 別中央値は **0日から200日超**まで開いている
- **既定LT（この環境では5日）を超える SHOP が 133 / 153**。
  それらを通る工程が全サンプルの **72.6%** を占める
- 一律の日数でカバーできる分布ではない、というのがデータからの結論

ただし **実績をそのまま全 SHOP に適用すると赤が 7,986 → 15,332 件に倍増する。**
インターバルに外注滞留や材料待ちが丸ごと入っていること、分位点を残工程分そのまま
足し上げると悲観に寄ることが原因。詳細と対応方針は
[フェーズ2_実績リードタイム.md](フェーズ2_実績リードタイム.md) §5.2。

なお `工程着手日付` → `工程完了日付` の差は中央値 0 日で、これは「作業実施日」の記録。
リードタイムとして使うなら**工程間インターバル**を採るべき。

### 2.5 LT算出方式をプラガブルにする（B を実装済み）

| 方式 | 計算 | 必要データ | 状態 |
|---|---|---|---|
| A. 固定（現行） | `m_shop_lt` or `SHOP_LT_DAYS` | なし | 実装済 |
| **B. 実績ベース** | SHOP別 実績LT の p50 / p75 / p90 | **今あるデータのみ** | **実装済** |
| C. Hs ベース | 待ち日数 + Hs ÷ 有効稼働時間 | Hs取込（済）+ キャパマスタ | 未 |
| D. ハイブリッド | 実績の待ち日数 + Hs項 | B + C | 本命 |

B は `m_param.LT_MODE = fixed | actual` で切り替える。既定は `fixed`。
実績値は「推奨値」として画面に出し、**納得した SHOP だけ `m_shop_lt` に採用する**
運用にした。手入力がある SHOP は実績より手入力を常に優先する。

残っているのは、部品詳細の「なぜこの状態か」に**方式別のバッファを併記**すること。
「固定なら +3日（緑）だが実績なら −6日（赤）」を見比べられると、切り替えの
説得力が出る。

### 2.6 客先に確認したいこと（C・D に進む前）

- Hs の単位は人時か時間か（複数人作業の扱い）
- Hs は正味作業のみか、段取りを含むか
- 実績工数（Hs 消化率）が別途取得できるか
- SHOP ごとの要員数・稼働時間が取得できるか

## 3. スマートフォン対応

### 3.1 方式

既存 PC 画面のレスポンシブ化ではなく、**`/m/*` にモバイル専用ルートを新設**する。

既存一覧は `@tanstack/react-table` の11列テーブル前提でレスポンシブ化しても使えない。
専用ルートなら **PC 版に一切手を入れずに済み**、API は `/api/parts` をそのまま使えるので
バックエンド改修もほぼ不要。スマホ幅で自動振り分け、PC 版へのリンクは残す。

マスタ・取込・担当者・監査は `/m` 配下に置かない（サイドバー自体を作らない）。

### 3.2 受信箱（`/m`）

メールアプリの体験に寄せる。

```
┌──────────────────────────────┐
│  部品   [すべて][要対応 12][困りごと 3]  🔍 │
├──────────────────────────────┤
│ ● 🔴 −6日   残12日          37B │
│   MANIFOLD ASSY                  │
│   V38B55114-111 #7827            │
│   ▸ 7P21 機械加工 / 滞留 8日      │
├──────────────────────────────┤
│ ● 🔴 −3日   残20日          37B │
│   KNOCK PIN            📝困りごと │
│   TJV38B21005-103 #2701          │
│   ▸ 82P0 表面処理 / 滞留 25日     │
└──────────────────────────────┘
```

- 既定の並びは優先度順（色 → バッファ昇順 → 滞留降順）。既存の `sevRank` を流用できる
- 上部セグメントで「要対応 / 困りごと / 自分の担当」を切替。工程員は自分の担当機種が既定

### 3.3 スワイプ操作

- **右スワイプ（緑）＝ 確認済み**。その日の受信箱から消える（メールのアーカイブ相当）
- **左スワイプ（橙）＝ 困りごとを立てる**。テンプレ選択のボトムシートが出る
- 閾値を超えたら確定、途中で離せば戻る。確定後は5秒間「元に戻す」トーストを必ず出す
  （誤操作が怖くて使われなくなるのを防ぐ）
- ライブラリ追加は不要。Pointer Events で自前実装できる規模

既存の `t_shelved`（一旦置き）は**無期限の保留**で意味が違う。「今日は確認したから消す」を
shelved に流用すると PC 版の保留一覧が汚れるため、別テーブルにする。

```
t_ack ( os_id, user_id, acked_at, ack_until )   -- 既定で翌稼働日の朝まで
```

### 3.4 困りごとテンプレート

```
m_trouble_template ( id, label, sort_order, active, requires_note )
t_trouble          + template_id
```

初期値案：材料未入荷 / 前工程の遅れ / 外注戻り遅れ / 図面・仕様待ち /
治具・設備トラブル / 検査待ち・不適合 / 人員不足 / その他（メモ必須）。
管理者が PC のマスタ画面から編集する。

効果は入力の速さだけではない。**困りごとが分類データになるので集計できる。**
「今月の困りごとの42%が外注戻り遅れ」「SHOP 82P0 は材料未入荷に偏っている」が出せる。

### 3.5 詳細（`/m/parts/:id`）

工程タイムラインを縦カード、判定根拠、困りごと、対応メモの順。
画面下部に固定のアクションバー（確認済み / 困りごと / メモ）。

工場利用を考えると、JWT Cookie の有効期限と圏外時の挙動は別途詰める必要がある。
PWA 化（manifest + Service Worker でオフライン閲覧）は初期スコープ外とする。

## 4. これまで検知できていないリスク

現状の検知は バッファ / 滞留日数 / 赤紙 / 子部品欠品 / 外注ステータス の5つで、
いずれも**「今この瞬間」のスナップショット**であり、計画データの正しさを前提にしている。

### 4.1 悪化速度の検知（最優先。急ぐ理由がある）

`t_part_status` は再計算のたびに上書きされ、履歴を持たない。そのため
**「先週まで緑だったのに急に黄になった部品」と「3ヶ月ずっと黄の部品」が区別できない。**
前者の方が圧倒的に危険。

```
t_status_history ( os_id, snapshot_date, buffer, color, days_left,
                   remain_shops, current_shop, final_due, total_shops )
```

ここから出せるもの：

- バッファ悪化速度（1週間で何日減ったか）
- **納期の変更検知**（`final_due` が動いた＝客先要求変更か計画変更）
- **工程数の増加検知**（`total_shops` が増えた＝手戻り・追加工程の可能性）
- 色の遷移履歴（緑→黄→赤の予兆）

> **履歴は溜め始めないと過去に遡って作れない。** テーブル追加と日次バッチだけなら
> 画面への影響はゼロなので、8月末リリース前に `main` へ入れることも検討したい。

### 4.2 手戻り検知

同一 SHOP を2回以上通る / `wip_flag` が前の工程順に戻る /
`actual_end` が入っていた工程の実績が消える。いずれも不適合・やり直しのシグナル。
手戻りは納期遅延の最大要因の一つだが、現状まったく見えていない。

### 4.3 外注先ごとの遅延傾向

`m_vendor.return_lt`（標準戻りLT）という列は既にあるが、**算出に一切使われていない**。
実績の `out_date` → `in_date` を集計すれば外注先別の実績戻りLTと遅延率が出せる。
「この外注先は標準より平均+8日遅れる」が分かれば発注時点で先手が打てる。
`eta_date` を過ぎても `in_date` が来ない部品の日次アラートも今すぐ作れる。

### 4.4 データ品質チェック

計画データ自体がおかしい部品は判定結果が信用できない。

- `plan_end < plan_start`
- `plan_start` が過去なのに `wip_flag` が立っていない
- `final_due` が既に過去
- 工程が0件
- SHOP が `t_shop_master` に未登録

これらを並べた「要確認データ」一覧を作る。地味だが、
**バッファが緑でも計画が壊れているだけ、というケースを潰せる。**

### 4.5 波及リスク（§1 と接続）

ある部品が特定 SHOP で滞留していると、同じ SHOP を待つ後続 N 件に波及する。
ヒートマップの集計基盤があれば「この部品の遅れは他17件に影響する」という**影響度**を
出せる。単体のバッファだけでは決められない優先順位。

### 4.6 沈黙検知

「担当未割当のまま14日」「困りごとを立てたまま7日メモ更新なし」
「`t_routing` に更新がないまま30日」。最後のものはデータ連携が止まっている検知にもなる。

### 4.7 納期集中

同一週に最終納期が集中している部品群。ヒートマップの縦軸を納期週にしたもので、
実装コストはほぼゼロ。

### 4.8 提示の仕方

これらを1つの「リスクスコア」に統合するのは**初期は避ける。**
複合スコアはブラックボックス化して現場の納得が得られず、「なぜこの部品が上位なのか」に
答えられなくなる。個別アラートを並べた「アラートセンター」から始め、
現場がどれを実際に見るかを観察してから重み付けを考える。

## 5. 進め方

実装済み（`develop`）:

- **1 ヒートマップ** — `/heatmap`
- **2.5-B 実績LT集計 + Hs取込** — `/lt`

残りの推奨順序:

1. **4.1 スナップショット履歴** — 履歴は今日から溜めないと取り返せない。
   テーブル追加と日次バッチだけで画面影響がないので、8月末リリース前に `main` へ
   入れることも検討したい
2. **外注工程の切り分け** — 実績LTの精度を上げる本丸（実績リードタイム §9.2）。
   `m_vendor.return_lt` が未使用のまま残っているので 4.3 とまとめて片付く
3. **3 スマホ対応** — 他と独立、並行可能
4. **部品詳細へのヒートマップ埋め込み** — 客先資料の ①② に対応（本書冒頭の対応表）

## 6. ブランチ運用上の注意

`main` が8月末リリースのため、`develop` では Prisma マイグレーションが衝突しやすい。

- 新規マイグレーションのファイル名に日付プレフィックスを必ず付ける
- `main` からの取り込みは rebase ではなく **merge** に統一する
- 検証環境の DB は本番と共有しない
